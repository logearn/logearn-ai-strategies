# Pro 版分析能力扩展 — 设计文档

基于现有 `tool.html`（收益与快照字段关系分析工具）的架构设计，覆盖 5 个新分析模块 + Pro 门控机制。**本文档只做设计，不含实现代码**，但会明确指出应复用哪些现有函数/组件，方便后续直接开发。

---

## 0. 整体设计原则

### 0.1 数据流保持不变
所有新功能都基于现有的全局工作集 `activeRows`（应用了"全局条件过滤"之后的数据），而不是 `matchedRows`（原始全量数据）。这样用户在顶部设置的过滤条件会自动联动到 Pro 功能，行为上和现有的"相关性/散点图/分箱图"完全一致，用户不需要学习新的心智模型。

字段读取统一走现有的 `getFeature(row, field)`，分类字段用现有 `ROW_LEVEL_FIELDS`（`symbol`/`signalType`/`id`/`token_address`），数值字段用现有 `scatterOptions`。

### 0.2 面板复用现有折叠面板样式
每个新功能是一个独立的 `.panel` + `.panel-header-row`（复用现有折叠展开逻辑 `document.querySelectorAll('.panel-header-row[data-target]')`），插入位置：

```
数据源
全局条件过滤 & 筛选 CA
总览统计
字段与收益相关性
├─ [新增] 相关性矩阵 / 热力图        ← 紧跟在单变量相关性表后面，逻辑上是它的扩展
├─ [新增] 多元回归特征重要性          ← 同上，作为"相关性分析"大类的第三个子面板
散点图分析
分箱柱状图
├─ [新增] 分类字段对比（箱线图/胜率表） ← 和分箱柱状图同属"分布对比"类，放在它附近
├─ [新增] 分组对比分析                ← 依赖相关性计算，但视角是"分组"，放在较后位置
├─ [新增] 时间维度分析                ← 引入新的时间轴维度，放在最后
```

### 0.3 Pro 门控机制（软门控，纯前端）

新增一个全局状态：

```js
const PRO_STATE = { isPro: false, licenseKey: null };
const PRO_FEATURES = new Set([
  'corrMatrix', 'groupCompare', 'regression', 'timeAnalysis', 'categoryCompare',
  'featureInteraction', 'multiStrategy', 'similarCase',
  'customFeature', 'snapshotCompare', 'reportExport'
  // 注意：字段质量总览(6.1)、异常值报警(6.2)、收益分布直方图(7.1)、
  // 归因累计曲线(7.2)、非线性关系检测/Spearman(8.1)、最优分箱推荐(8.2)
  // 建议放 Free 版，不加入这个集合，理由见文档第 6/7/8 节说明
]);
```

每个 Pro 面板外层包一层 `.pro-panel-wrap`：

- **未解锁**：面板标题旁显示 👑 PRO 徽标；面板体（`.panel-body`）内容替换为「锁定态」——用 `filter: blur(6px)` 的示例图 + 半透明遮罩 + 居中卡片（说明这个功能能看到什么、解决什么问题 + "升级 Pro" 按钮），不渲染真实计算（避免免费用户绕过 UI 直接从 DOM/内存里读到真实结果）。
- **已解锁**：正常渲染，和现有面板体验一致。

顶部 `app-header` 里现有主题切换按钮旁边加一个 Pro 状态徽标（"Free 版" / "⭐ Pro 已解锁"），点击可打开升级说明弹窗（占位，实际接入取决于后续是否有账号体系/支付渠道）。

> **重要说明（如实告知，不要含糊）**：这是纯前端单文件工具，没有后端账号体系。上述门控本质上只是"隐藏 UI + 不触发计算"，属于软门控（deterring casual users），并不是真正的安全边界——只要用户会改浏览器里的 JS 变量或者看到过网络请求里的原始 JSON，一样能拿到数据。如果要做到真正的 Pro 权限控制，至少需要：① 服务端做鉴权和计算（把这几个计算量较大的功能挪到后端 API），或 ② 前端引入 license key 校验但接受"防君子不防小人"的现实。设计上先做软门控上线验证付费意愿，是合理的第一步，但不要把它当成商业机密数据的保护手段。

### 0.4 与现有代码的复用清单

| 复用对象 | 现有函数/组件 | 新功能里怎么用 |
|---|---|---|
| 皮尔逊相关系数 | `pearson(pairs)` | 相关性矩阵、分组对比、回归里的两两相关都直接调用 |
| 线性回归（单变量） | `linearRegression(pairs)` | 多元回归里作为简化版正规方程求解的基础，或用于回归诊断图 |
| 字段取值 | `getFeature(row, field)` | 所有新功能统一入口，不重新实现 |
| 字段中文说明 | `getFieldDesc(field)` | 热力图/回归系数表的字段名 tooltip |
| 多选标签输入 | `attachAutocomplete` + `.tag-input`/`.tag-chip` 组件（散点图 X 指标多选那一套） | 相关性矩阵选字段、回归选自变量都复用这套交互，不用重新做输入组件 |
| 深色/浅色 Plotly 主题 | `darkLayout(layout)` | 热力图、箱线图、时间序列图统一走这个，保证配色一致 |
| 离群点裁剪 | `computeClipRange` / `tukeyFence` | 箱线图、时间序列散点可选复用，避免极端值把图压扁 |
| p 值近似计算 | `pearsonPValue` / `erf` / `normalCdf` | 分组对比显著性、回归系数显著性都复用同一套正态近似，不重复造轮子 |
| 折叠面板 | `.panel-header-row[data-target]` 事件绑定 | 5 个新面板直接套用，不需要新写展开收起逻辑 |
| CA 高亮查找 | `highlightCAs` | 热力图点击某个格子跳转散点图后，高亮框依然生效 |

## 1. 多变量相关性矩阵 / 热力图

### 目标问题
单变量相关性表只能看"字段 A 和收益的关系"，看不出"字段 A 和字段 B 是不是在说同一件事"。如果两个高度共线的字段都被当成独立的强特征，会高估信号数量、也会让后续多元回归的系数不稳定。

### 面板位置
紧跟在现有「字段与收益相关性」面板下方，作为同一大类的第二个子面板：`相关性矩阵（Pro）`。

### 交互设计
- 顶部一个多选标签输入框（复用散点图 X 指标多选组件），默认预填「相关性表 Top 10 字段 + returnCurrent + returnMax」。
- 字段数量上限提示：超过 20 个字段时输入框旁给出黄色提示"字段过多会导致矩阵拥挤且计算变慢，建议控制在 20 个以内"，但不强制拦截。
- 一个"生成矩阵"按钮（避免每加一个标签都重新算一次 O(n²) 相关性，控制计算时机）。
- 矩阵下方一行开关：`只高亮 |r| ≥ 0.8 的共线对`（默认开）。

### 计算逻辑
对选中的 K 个字段，两两组合（含自身对角线 r=1）调用 `pearson()`，每对只用两个字段都非空的行（`getFeature` 取值 + `Number.isFinite` 过滤），复杂度 O(K² × N)，K≤20 时在几千行数据量级下前端计算可接受。

同时基于矩阵派生一个"共线对列表"：遍历上三角矩阵（不含对角线），筛出 `|r| ≥ 0.8`（阈值可配置）的字段对，按 |r| 降序列成表格，每行显示两个字段名 + r 值 + 一句自动生成的提示："这两个字段可能在描述同一件事，同时作为独立特征使用需谨慎"。

### 可视化输出
- 主体是一个 Plotly `heatmap`（`darkLayout` 主题），x/y 轴都是选中字段名（做换行/旋转避免重叠），colorscale 用发散色系（如 RdBu，中心 0 白色/中性色），每个格子内用 `annotations` 标注 r 值保留两位小数。
- 格子上加点击事件：点击非对角线格子 → 把这两个字段分别设为散点图的 X 和 Y（复用现有相关性表里"设 X,Y"按钮的逻辑），并滚动到散点图区域，方便立刻钻取查看具体分布。
- 矩阵下方是前面提到的"共线对列表"表格，作为热力图的文字化摘要（照顾不习惯读热力图的用户）。

### 边界情况
- 某个字段在当前 `activeRows` 里全部缺失（比如过滤后子集刚好都没有该字段）→ 该行/列显示为灰色斜纹格 + "数据不足"，不参与共线对列表。
- 单字段方差为 0（所有样本取值相同）→ `pearson` 分母为 0，返回 0，这种情况在矩阵里用统一浅灰色标注并加 tooltip"该字段在当前样本中无变化，相关性无意义"，避免被误读成"确实不相关"。

## 2. 分组对比分析

### 目标问题
整体样本上算出来的"字段 A 与收益强相关"，可能只是因为某一类信号（比如某个 `signalType`）恰好贡献了大部分正收益样本，把其他类型的噪声掩盖了。不分组直接下结论容易得出"伪相关"。

### 面板位置
新面板：`分组对比分析（Pro）`，放在分箱柱状图之后。

### 交互设计
- 分组维度选择：下拉框，默认给 `signalType`、`platform`（如果 `scatterOptions`/`colorOptions` 里有对应字段就动态列出），也支持选一个数值字段 + 手动输入分箱断点（复用现有分箱柱状图的断点输入框逻辑），把数值字段离散化后当分组维度用（比如按 `swap_begin_time` 分成"上午/下午/晚上"这种场景可以用这个通道，和第 4 点的时间维度分析形成互补，不重复实现）。
- 目标字段选择：沿用现有相关性表的多选（可以直接"从相关性表 Top N 一键导入"，减少重复选择的操作成本）。
- 目标收益选择：`returnCurrent` / `returnMax`，同现有 `corrTarget`。
- 最小样本量阈值输入框（默认 10）：低于该阈值的分组不计算相关性，直接标"样本不足"，避免小样本极端 r 值误导。

### 计算逻辑
对每个分组值，从 `activeRows` 里筛出该组的子集，对每个目标字段调用和现有 `computeCorrelations` 相同的逻辑（`pearson` + 样本量过滤），得到「字段 × 分组」的 r 值矩阵，同时保留整体（未分组）的 r 值作为对照列。

**伪相关识别规则**（自动标注，不需要用户手工判断）：
- 整体 |r| ≥ 0.3 但所有分组内 |r| 都 < 0.15 → 标注"⚠️ 整体相关性可能是分组间均值差异导致的合成效应（辛普森悖论），单个分组内没有独立解释力"。
- 整体 r 符号和某个占比最大分组的 r 符号相反 → 标注"⚠️ 该分组与整体趋势方向相反，请单独核查"。

### 可视化输出
- 主表：行 = 字段，列 = 各分组 + 整体，单元格 = `r (n)`，按整体 |r| 排序；单元格背景色按 r 值深浅着色（复用矩阵那套发散色）。
- 每行末尾一个"查看分组对比图"按钮，点击后在下方渲染一个分组柱状图（x=分组，y=该字段与目标的 r 值，柱子颜色按正负区分），方便直观看出哪个分组在拉高/拉低整体相关性。
- 触发了伪相关规则的行，行首加 ⚠️ 图标 + hover tooltip 显示具体判断依据。

### 边界情况
- 分组值为 `null`/空字符串（比如 `platform` 缺失）→ 归入统一的"（空）"分组，不丢弃样本，但在表格里排在最后并做浅色区分。
- 分组数量过多（比如按 `token_address` 误选成分组维度）→ 检测到分组数超过 30 时提示"该字段分组数过多，可能不适合作为分组维度，建议换成分类字段或先分箱"。

## 3. 特征重要性排序（多元线性回归）

### 目标问题
现有相关性表是单变量排序，没法回答"控制住其他变量后，这个字段还有没有独立的解释力"——两个高度共线的字段可能在单变量表里都排前面，但多元模型里其中一个的系数会被"吃掉"。

### 面板位置
新面板：`多元回归特征重要性（Pro）`，紧跟在相关性矩阵面板之后（三者共同构成"相关性分析"大类：单变量 → 两两共线 → 多元联合）。

### 交互设计
- 自变量多选（复用标签输入组件），提供"从相关性矩阵的共线对列表里自动排除一个"的快捷操作——即如果用户选中的字段里存在被标记为高度共线的对，给出提示"检测到 X 和 Y 高度共线（r=0.91），同时放入回归可能导致系数不稳定，建议只保留一个"，但不强制阻止运行。
- 因变量：`returnCurrent` / `returnMax`。
- 开关：`使用标准化系数`（默认开，即先对每个自变量和因变量做 z-score 标准化再回归，得到的 β 可以跨字段比较大小，这是本功能的核心价值——单变量 r 和标准化回归系数放在一起看，才能分清"真实独立贡献"和"因为跟别的强字段共线而显得重要"）。
- 按钮：`运行回归`（计算量比前两个功能大，不做实时联动，显式触发）。

### 计算逻辑
1. 取自变量集合 + 因变量，只保留所有选中字段都非空的行（listwise deletion），显示实际使用的样本量 n（如果 n 相比 `activeRows` 总量掉得很多，需要用醒目文字提示"因缺失值剔除了 X% 的样本，结果可能有偏"）。
2. 标准化：每个自变量、因变量分别做 `(x - mean) / std`。
3. 用最小二乘正规方程 `β = (XᵀX)⁻¹ Xᵀy` 求解标准化系数，矩阵求逆用高斯-约当消元（自变量数 ≤ 20 时浏览器端计算完全可行，不需要引入额外的线性代数库）。
4. 计算模型整体 R² 和调整 R²（用于告诉用户"这些字段一共能解释收益变化的百分之多少"，避免高估单个字段的作用）。
5. 简易 VIF（方差膨胀因子）：对每个自变量，用它对其余自变量做回归得到的 R²ᵢ，`VIF = 1 / (1 - R²ᵢ)`，VIF > 5 标黄，> 10 标红，直接在系数表里给出"共线性警告"列，呼应第 1 点的相关性矩阵。
6. 可选"逐步回归（前向选择）"模式：从空模型开始，每一步加入能让调整 R² 提升最多的一个候选字段，直到没有字段能带来有意义的提升（比如提升 < 0.01）或达到用户设置的字段数上限，最终展示"入选顺序"，帮助用户理解哪些字段是"增量信息"，哪些字段加进来后已经不再提升模型（往往是因为已经被前面的字段解释掉了）。

### 可视化输出
- 横向条形图：y 轴是字段（按 |β| 降序），x 轴是标准化系数 β，正负用不同颜色（复用现有 palette），条形旁标数值。
- 系数表：字段｜β｜VIF｜单变量 r（对照）｜共线性警告。把"单变量 r"和"多元 β"并排放，是这个面板最核心的教育价值——一眼看出哪些字段是"单看显著、放一起就消失"的伪强特征。
- 模型摘要卡片：n（实际参与样本数）、R²、调整 R²、一句自然语言总结（如"这 8 个字段合计能解释收益方差的 34%"）。

### 边界情况
- 自变量数 ≥ 样本数（列多于行，矩阵不可逆）→ 直接拦截并提示"自变量数量不能超过可用样本数，请减少字段或放宽过滤条件"。
- 矩阵接近奇异（高度共线导致数值不稳定）→ 求逆前做一个条件数检测，条件数过大时提示"由于字段间共线性极高，回归系数可能不稳定，建议参考 VIF 列先剔除冗余字段"，而不是直接输出一个看似精确实则没有意义的系数。

## 4. 时间维度分析

### 目标问题
`swap_begin_time` 目前只用来做 calls/snapshots 的时间最近匹配，没有被当作分析维度用过。策略的有效性可能会随时间/市场环境漂移，只看"全期样本整体胜率"会掩盖"策略其实已经失效了一段时间"这种情况。

### 面板位置
新面板：`时间维度分析（Pro）`，放在最后（时间维度是独立于其他分析的新增视角）。

### 交互设计两个子视图，用 tab 或并列展示：

**子视图 A：时间分桶胜率/收益趋势**
- 粒度选择：按小时 / 按天 / 按周（用 `swap_begin_time` 换算成对应粒度的桶）。
- 图表类型：类似现有分箱柱状图，但 x 轴是时间桶而不是数值区间。

**子视图 B：相关性随时间漂移（滚动窗口）**
- 选择一个字段（沿用现有联想输入）。
- 窗口大小输入（比如"7 天"）+ 步长输入（比如"1 天"）。
- 对每个滚动窗口内的子集重新计算该字段与所选收益目标的 Pearson r，串成一条时间序列。

### 计算逻辑
- 分桶：把 `swap_begin_time`（Unix 秒）按粒度取整（小时=整除 3600，天=整除 86400，周=按 ISO 周），分组逻辑复用第 2 点"分组对比分析"里已经设计好的分组计算框架（时间桶本质上也是一种分组维度，避免重复设计一套聚合逻辑）。
- 每个桶计算：样本数 n、胜率（`returnCurrent > 1` 的占比，复用 `calcStats` 里已有的胜率计算）、平均倍数、中位数倍数。
- 滚动相关性：按时间排序后用滑动窗口切片调用 `pearson()`，同时记录每个窗口的 n，窗口 n 过小（<10）的点在图上用空心/半透明标记，提示这段时间数据量不足以支撑稳定的相关性估计，避免用户把小样本的剧烈波动误读成"信号真的变了"。

### 可视化输出
- 子视图 A：双轴图——柱状图（左轴，样本数 n）+ 折线图（右轴，胜率 %，和/或平均倍数），复用 `darkLayout` 双 y 轴配置；下方给出文字摘要，比如自动检测"最近 N 个桶的胜率相比历史均值下降超过 X 个百分点"时给出提示。
- 子视图 B：折线图，x = 窗口结束时间，y = 该窗口内的 r 值，用阴影带表示样本量不足的区间（而不是真正的置信区间，避免和现有散点图里"95% 置信区间"的语义混淆，这里改用"低置信度区间"这个说法+ 灰色阴影，含义是"这段的 r 值本身不稳定，不代表趋势置信区间"）。
- 两个子视图都支持导出当前时间序列为 CSV（复用现有 `csvEscape`/下载逻辑）。

### 边界情况
- 时间跨度过短（比如全部样本集中在 1 天内）→ 提示"当前样本时间跨度不足以进行有意义的时间维度分析，建议放宽全局过滤条件"。
- 窗口设置导致窗口数过多（比如窗口 1 小时、步长 1 分钟、数据跨 30 天）→ 前端限制最大窗口数量（比如 200 个），超过时提示用户调大步长。

## 5. 分类字段（signalType / platform）与收益关系

### 目标问题
目前分类字段只能作为散点图的"颜色"维度，颜色区分度有限、也看不到分布形状和统计显著性，没法直接回答"哪个信号类型/平台的收益分布明显更好，这个差异是不是统计上站得住脚"。

### 面板位置
新面板：`分类字段对比（Pro）`，放在分箱柱状图附近（同属"看分布"的功能组）。

### 交互设计
- 分类字段选择：下拉，默认列出 `signalType`、`platform`，同时允许把任意数值字段通过断点转成"伪分类"（复用现有分箱柱状图断点输入组件，逻辑上和第 2 点"数值分组"共用同一套离散化代码，不重复实现）。
- 目标数值字段：`returnCurrent` / `returnMax` / 任意 `scatterOptions` 字段。
- 显著性检验开关：默认开，两组用 Welch's t 检验（不假设方差相等，更稳健），三组及以上用单因素方差分析（ANOVA）的简化 F 检验；检验用到的正态近似复用现有 `erf`/`normalCdf`。

### 计算逻辑
- 分组：按分类字段值把 `activeRows` 切片（同样复用第 2 点的分组框架）。
- 每组统计量：n、均值、中位数、标准差、四分位数（`calcStats` 已经实现大部分，直接复用）、胜率。
- 显著性：
  - 两组：Welch's t = (mean1-mean2) / sqrt(s1²/n1 + s2²/n2)，自由度用 Welch–Satterthwaite 近似，p 值用现有正态近似（样本量较小时这是简化处理，会在文案里注明"大样本近似，n 较小时结果仅供参考"）。
  - 多组：简化单因素 ANOVA，算组间方差、组内方差、F 统计量，p 值同样用正态近似简化（不追求和专业统计软件完全一致，目标是"给用户一个大致的显著性方向感"，文案上明确这是简化版）。

### 可视化输出
- 主图：Plotly `box` 箱线图，x = 分类值，y = 目标字段，显示中位数/四分位/离群点（可选复用 `computeClipRange` 收紧 y 轴范围，避免极端离群点压扁箱体）。
- 副图/表：胜率对比条形图 + 汇总表（n / 胜率 / 均值 / 中位数 / 标准差），表格支持按胜率或均值排序。
- 显著性结果用一行文字摘要展示在图表上方，例如"signalType 各组间收益差异显著（p=0.02 < 0.05），其中 `v_breakout_volume` 组均值显著高于其余组"，而不是让用户自己去读 F 值/t 值这类原始统计量。

### 边界情况
- 某个分类下样本数 < 5 → 该类别在箱线图里仍然显示，但汇总表里胜率/均值那一列标"样本过少，仅供参考"，且不纳入显著性检验（避免极小样本拉低整体检验的可靠性）。
- 分类值过多（比如超过 15 类）→ 提示"类别过多不利于阅读，建议只保留样本量前 N 大的类别，其余归并为'其他'"，并提供一键归并按钮。

## 6. 数据质量类（建议 Free 版）

这两个功能不算"分析能力"，更像是所有分析的地基——用户如果看不到数据本身有多脏，前面 1-5 点算得再精巧也会建立在错误的样本上。**建议放在免费版**，作为对 Pro 分析结果可信度的背书，也能反过来提升 Pro 转化（用户先在免费版里看到自己数据的质量问题，才会更认可付费功能给出的结论）。

### 6.1 字段缺失率 / 覆盖率面板

**目标问题**：相关性表里经常混进"当前 100 条样本里只有 20 条有值"的字段，算出来的 r 和 n 虽然都展示了，但 n 藏在表格角落里不显眼，用户很容易忽略样本量差异直接对比不同字段的 r 值。另外还有"常量字段"（比如所有样本这个字段取值都一样）——`pearson` 对这种字段返回 0，看起来像"完全不相关"，但真实含义是"这个字段在当前数据里没有信息量"，两者需要区分开。

**面板位置**：新面板 `字段质量总览`，建议放在"总览统计"和"字段与收益相关性"之间——用户看完总体样本数后，第一件事应该是了解字段本身靠不靠谱，再去看相关性排序。

**交互设计**：一张可排序表格，默认按覆盖率升序排列（最先暴露问题字段）；顶部一个"只看有问题的字段"开关（覆盖率 < 50% 或方差为 0）。

**计算逻辑**：遍历 `allNumericKeys`（以及 `ROW_LEVEL_FIELDS`），对每个字段统计：
- 覆盖率 = 非空非 NaN 样本数 / `activeRows.length`
- 唯一值数量（数值字段可以用去重后 `Set.size`，超过一定数量直接标"连续型"不用精确去重计数，避免大数据量卡顿）
- 是否常量（唯一值数量 = 1）
- 均值/标准差（复用 `calcStats` 的部分逻辑）

**可视化输出**：表格列 = 字段名｜中文含义（复用 `getFieldDesc`）｜覆盖率（带进度条底色）｜唯一值数｜标记（🔴常量 / 🟡低覆盖 / 🟢正常）。点击字段名可以直接跳转到相关性表定位该字段，方便交叉核对。

**边界情况**：`activeRows` 为空时整个面板隐藏（复用现有面板显隐逻辑）；覆盖率计算要用当前的 `activeRows`（过滤后数据集）而不是 `matchedRows`，否则用户调整过滤条件后这里的数字对不上。

### 6.2 异常值 / 数据质量报警

**目标问题**：现有代码里已经有"离群点裁剪"（Tukey IQR），但那个是为了让散点图好看，不是为了发现数据本身错没错。比如 `returnCurrent` 出现负数、`current_mcap` 是 0 但 `initial_mcap` 不是 0 这种**逻辑矛盾**，本质是数据管道的 bug 或者极端边缘 case，会悄悄参与所有下游统计但没人知道。

**面板位置**：紧跟在 6.1 字段质量面板下方，作为同一个"数据质量"大类的第二个子板块。

**交互设计**：一份"待核查记录"清单表，默认收起，标题显示命中条数（比如"⚠️ 发现 3 条可能存在数据问题的记录"），点击展开。清单支持"从工作集中排除这些记录"一键操作（生成一个隐藏的排除名单，作用类似全局过滤但专门针对数据问题记录，不占用现有过滤条件行）。

**计算逻辑**：内置一组硬编码规则（后续可以做成可配置，但第一版硬编码即可覆盖大部分场景）：
- `returnCurrent <= 0` 或 `returnMax <= 0`（收益倍数理论上应该 > 0）
- `returnMax < returnCurrent`（逻辑上"期间最大值"不应该小于"当前值"）
- 关键数值字段为负但语义上不该为负（比如 `pool_liquidity < 0`、`buyer_count_d1 < 0`）
- 时间戳字段明显不合理（比如 `swap_begin_time` 晚于 `signal_open_time`）

**可视化输出**：清单每行显示 symbol / CA / 命中的规则文字描述（比如"returnMax(0.8x) 小于 returnCurrent(1.2x)，逻辑矛盾"），而不是让用户自己去猜为什么这条被标出来。

**边界情况**：规则命中不代表数据一定是错的（也可能是极端但真实的市场情况），文案上用"可能存在问题"而不是"错误"，避免用户盲目删除真实数据。

## 7. 收益分布类

### 7.1 收益分布直方图 + 分位数表

**目标问题**：现有总览统计只给了均值和"胜率(倍数>1)"两个汇总数字，看不出分布形状。收益倍数天然是长尾分布（少数暴涨 token 把均值拉得很高），只看均值容易高估策略的"典型表现"。

**面板位置**：新面板 `收益分布`，建议紧跟在"总览统计"下方，作为它的可视化延伸。

**交互设计**：目标字段切换 `returnCurrent` / `returnMax`；一个"对数 X 轴"开关（默认开，因为倍数数据取对数后通常更接近正态、直方图更好看）；分箱数量可调（默认按 `Math.sqrt(n)` 自动计算，同现有分箱柱状图的默认分箱数逻辑）。

**计算逻辑**：对选中字段的 `activeRows` 取值数组排序，用 `percentile()`（现有函数）算出 P10/P25/P50/P75/P90/P99，直方图分箱统计每个区间的样本数（对数轴时先对数值取 `log10` 再分箱）。

**可视化输出**：Plotly `histogram`（`darkLayout` 主题），叠加几条垂直虚线标出中位数和均值的位置（两条线明显分开时可以直接给出文字提示"均值明显高于中位数，说明收益分布右偏，少数极端案例拉高了平均表现"）；下方一张分位数表格，横向陈列 P10 到 P99。

**边界情况**：`returnCurrent`/`returnMax` 恒为正，对数轴不会有 0 或负数问题，但如果用户把这个面板复用到其他可能含 0/负值的字段上（比如价格变化百分比），需要检测并自动关闭对数轴选项。

### 7.2 收益归因（累计收益曲线）

**目标问题**："平均倍数 2.3x" 这种汇总数字看不出策略的收益结构——是每个信号都稳定贡献一点，还是极少数几个 100x 的 token 撑起了几乎全部收益、其余大多亏损？这直接影响用户对策略"可持续性"和"仓位管理"的判断。

**面板位置**：紧跟在 7.1 收益分布面板之后。

**交互设计**：按 `swap_begin_time` 排序后，横轴是信号发生顺序（或时间），纵轴是"累计收益贡献"；一个开关"假设等仓位定投"（每笔信号权重相同，累加 `returnCurrent - 1` 作为收益贡献）vs "按 mcap 加权"（用 `initial_mcap` 归一化后加权，更贴近真实资金分配场景，可选，复杂度较高，可作为二期）。

**计算逻辑**：按时间排序后计算累计和 `cumsum(returnCurrent_i - 1)`，同时单独计算"前 5% 贡献占比"（帕累托集中度指标）：把每笔信号的收益贡献降序排列，看排名前 5% 的信号贡献了总收益的百分之多少。

**可视化输出**：一条累计收益曲线（Plotly `scatter` mode lines）；旁边一张小卡片直接给结论，比如"Top 5% 的信号贡献了 68% 的总收益，其余 95% 信号平均贡献接近于 0"，把统计结果翻译成一句话，而不是让用户自己去读曲线形状。

**边界情况**：这个功能对"信号顺序"敏感，如果 `swap_begin_time` 缺失或大量重复（同一时刻大量信号），累计曲线的横轴意义会打折扣，需要在缺失率较高时（复用 6.1 的覆盖率计算）给出提示。

## 8. 特征工程辅助类

### 8.1 非线性关系检测（Spearman 秩相关）

**目标问题**：现有相关性表全部基于 Pearson（线性相关），如果字段和收益之间是 U 型、对数型或者其他单调但非线性的关系，Pearson r 会显著低估甚至掩盖这种关系，导致真正有用的字段排名靠后甚至被忽略。

**面板位置**：不新增独立面板，而是**直接扩展现有"字段与收益相关性"表**——新增一列 `Spearman ρ`，以及一列 `|Δ|`（Pearson r 和 Spearman ρ 的绝对差值），默认按 `|Δ|` 也可排序。这样用户不需要切换视角就能顺手发现"这个字段可能是非线性关系"。

**交互设计**：表格列头新增排序选项；`|Δ|` 较大（比如 > 0.15）的行加一个 🔀 图标，hover 提示"该字段的线性相关性和单调相关性差异较大，可能存在非线性关系，建议在散点图里查看具体形状（可尝试打开对数轴）"。

**计算逻辑**：Spearman 秩相关的本质是"先把两列数据分别转成排名（rank），再对排名做 Pearson 相关"，直接复用已有的 `pearson()` 函数，只是输入换成排名而不是原始值——不需要新写相关系数公式，只需要新写一个排名转换函数（相同值取平均排名，即标准的 tied rank 处理）。

**可视化输出**：无需新图表，作为现有相关性表的增强列即可，改动成本很低。

**边界情况**：并列值（tied values）较多的字段（比如布尔型 0/1 字段）排名会有大量并列，标准 tied rank 处理后 Spearman 依然有效，但对这类字段本身用 Spearman 的意义不大，可以在字段是布尔/二值时直接不计算 Spearman（复用现有对 `isNumericColumn` 的判断逻辑，额外加一个"是否只有 2 个不同取值"的判断）。

### 8.2 最优分箱阈值推荐

**目标问题**：现有分箱柱状图的断点需要用户手动填数字（比如 `0.5,1,1.5,2`），全靠试错，效率低而且容易漏掉真正有区分度的分界点。

**面板位置**：在现有"分箱柱状图"面板的断点输入框旁边加一个 `自动推荐断点` 按钮（不新增独立面板，是对现有功能的增强）。

**交互设计**：点击按钮后，断点输入框自动填入推荐值，用户可以直接使用或者在此基础上手动微调；按钮旁一个小字提示"基于当前数值字段与目标收益的区分度自动计算"。

**计算逻辑**：用简化版的"单变量决策树分裂"思路——对分箱字段的取值排序，尝试若干候选分裂点（比如按分位数取 20 个候选点），每个候选点把样本分成两组，计算两组目标字段（`returnCurrent`/`returnMax`）均值的差异程度（比如组间方差 / 组内方差，思路和 8.1 的 ANOVA 简化版一致，可以直接复用第 5 点分类对比里已经设计的显著性检验代码），选出差异最大的 2-4 个分裂点作为推荐断点。这本质上是一个轻量级 CART 分裂逻辑，不需要引入完整的决策树库。

**可视化输出**：无需新图表，推荐结果直接回填到现有断点输入框，用户点"生成分箱柱状图"就能立刻看到效果，形成"推荐 → 预览 → 微调"的闭环。

**边界情况**：字段唯一值过少（比如只有 3 个不同取值）时，候选分裂点会退化，此时直接提示"该字段取值种类较少，建议直接手动设置断点"而不是勉强给出一个无意义的推荐。

### 8.3 特征交互探索（组合生成器）

**目标问题**：现有 7 个组装字段（`buy_sell_amount_ratio` 等）是开发者根据经验手工设计的。两个字段的比值/差值/乘积有时候比单独任何一个都更有解释力，但潜在组合数量很大，靠人工一个个试效率太低。

**面板位置**：新面板 `特征组合探索（Pro）`，放在"多元回归特征重要性"之后——逻辑上是先看单变量和多变量的现有字段表现，再用这个功能去"造"新字段。

**交互设计**：多选若干候选字段（建议不超过 10-15 个，避免组合数爆炸），勾选要尝试的组合方式（比值 A/B、差值 A-B、乘积 A×B），点击"生成并评估"；结果表默认按新组合与目标收益的 |r| 降序排列，只展示比原始两个字段单独的 r 都更强的组合（否则这个组合没有额外价值，没必要展示）。

**计算逻辑**：对选中的 K 个字段两两组合（K 个字段最多 K×(K-1)/2 对 × 3 种运算 = 组合数），每种组合动态生成一个衍生序列（逐行计算，跳过除以 0 的情况），复用 `computeCorrelations` 同款逻辑算出新组合与 `returnCurrent`/`returnMax` 的 r，同时记录原始两个字段各自的 r 值作为对照，只保留"新组合的 |r| 比两个原始字段里较大的那个还高至少 0.05"的结果（避免展示大量无意义的微弱提升）。

**可视化输出**：结果表：组合表达式（如 `mcap / holder_count`）｜新组合 r｜字段 A 单独 r｜字段 B 单独 r｜提升幅度；每行一个"加入组装字段库"按钮，点击后该组合会被加进当前 session 的自定义特征里，后续散点图/相关性表都能选到它（这个能力和第 10.2 点"自定义组装字段"复用同一套动态特征注册机制，不重复实现）。

**边界情况**：K 个字段选太多时（比如 15 个字段 × 3 种运算 = 315 种组合，每种组合都要跑一遍全量数据的除法+相关性计算），前端计算耗时会明显上升，建议加一个进度提示或者限制 K 上限（比如 10），超过时提示"字段过多，组合评估会比较慢，建议减少到 10 个以内"。

## 9. 样本 / 策略比较类

### 9.1 多策略对比

**目标问题**：`calls` 数据里的 `strategy_id` / `strategy_name` 字段目前完全没被用上。如果同一份数据里混合了多个策略的调用记录，现有的"总览统计"和"相关性分析"其实是把不同策略的样本混在一起算的，可能会互相稀释或掩盖各自的特征。

**面板位置**：新面板 `策略对比`，建议放在"总览统计"下方——用户了解完整体表现后，第一时间应该知道这个整体数字是不是被某个策略主导的。**如果数据里只有一个 `strategy_id`，该面板自动隐藏**，不占用界面空间。

**交互设计**：无需额外输入，自动按 `strategy_name`（或 `strategy_id`，展示时优先用有可读性的 name）分组，表格 + 图表默认展示。

**计算逻辑**：完全复用第 2 点"分组对比分析"里设计好的分组聚合框架，把分组维度固定成 `strategy_id`，本质上是那个通用模块的一个预设视图，不需要新写聚合逻辑。

**可视化输出**：策略对比表（n / 胜率 / 平均倍数 / 中位数倍数），外加一个"点击某个策略查看该策略专属的相关性排序"入口——点击后相当于临时把全局过滤加上 `strategy_id == 该策略`，直接复用现有 `applyFilter` 逻辑而不是另起一套。

**边界情况**：某个策略样本量极少（比如新策略刚上线只有 3 条记录）时，表格里该行的胜率/均值旁边加"样本过少，仅供参考"提示（复用第 5 点分类对比里已有的同款提示逻辑）。

### 9.2 相似 Case 检索（最近邻）

**目标问题**：面对一个新出现的信号，用户真正关心的问题往往是"历史上长得像这样的 token，后来涨跌如何"，而不是抽象的相关系数。这是一个从"统计规律"转向"具体案例参考"的功能，能直接辅助单个信号的决策，而不只是策略层面的复盘。

**面板位置**：新面板 `相似 Case 检索（Pro）`，放在"分类字段对比"附近（都属于"看具体分布/案例"的功能组），或者也可以设计成从散点图/相关性表"点击某个数据点"直接跳转过来的钻取入口，减少用户手动配置的成本。

**交互设计**：选择一个基准 token（从下拉/搜索框选，或者从散点图点击某个点直接带入）；选择用于计算相似度的字段集合（默认用相关性表 Top N 个字段，用户可调整）；返回最相似的 Top K 个历史 token（K 可调，默认 10）。

**计算逻辑**：对选中的字段先做 z-score 标准化（复用第 3 点多元回归里已经设计的标准化逻辑），计算基准 token 与其余所有 token 在标准化后特征空间里的欧氏距离（或者更简单的曼哈顿距离，计算量更小），按距离升序取 Top K。这是一个 O(N × K_fields) 的简单最近邻检索，不需要引入专门的向量检索库，前端直接算完全可行。

**可视化输出**：结果列表：symbol / CA / 相似度分数 / 该 token 的 `returnCurrent`/`returnMax`；额外给一个"这 K 个相似 case 的收益分布"迷你统计（均值、胜率），相当于"如果历史上这些相似情况平均涨了 X 倍，这次大概率……"这样一句可直接使用的参考结论（但文案上要谨慎，明确这是历史相似性参考，不是预测，避免用户误解为确定性结论）。

**边界情况**：如果基准 token 本身在关键字段上大量缺失，相似度计算会失真，需要提示"基准 token 的以下字段缺失，相似度计算未纳入这些维度"，列出具体字段名，让用户知道结果的局限性。

## 10. 可用性 / 协作类

这三个不涉及新的统计方法，但对日常使用的顺手程度影响很大，建议作为独立于统计能力的一条产品线并行推进。

### 10.1 分析快照保存 / 对比

**目标问题**：用户经常需要"这批新数据跑完之后，相关性和上一批比是变强了还是变弱了"，但现在每次都是从头分析，没有历史对照。

**面板位置**：全局功能，入口放在顶部 `app-header`（主题切换按钮旁边），而不是某个具体分析面板里——因为它作用于当前整体分析状态，不属于某一个子功能。

**交互设计**：`保存快照` 按钮：把当前过滤条件、Top 相关性结果、总览统计打包存一份，用户可以填一个备注名（比如"7月第一批数据"）；`快照列表` 面板：展示历史快照，支持勾选两份快照做"差异对比"。

**计算逻辑**：数据结构上是把 `activeRows` 摘要（不是全量原始数据，避免存储爆炸）+ 当前过滤条件 + `allCorrelations` Top N 结果序列化成 JSON，用之前讨论过的 `window.storage` 持久化能力存储（`shared=false`，个人数据）；对比时把两份快照的相关性表按字段名对齐，计算 r 值差异并高亮变化较大的字段。

**可视化输出**：对比视图是一张双栏表格（字段 | 快照A的r | 快照B的r | 变化量），变化量绝对值较大的行高亮，一眼看出"哪些字段的信号在变强/变弱"。

**边界情况**：两份快照如果字段集合不完全一致（比如数据结构升级新增了字段），对比表里缺失的一侧显示"该快照中不存在此字段"而不是报错或者留空造成误解。

### 10.2 自定义组装字段

**目标问题**：现有 7 个组装字段硬编码在代码里，用户如果想尝试一个新的比值/组合（比如 `mcap / holder_count`），现在只能等开发排期改代码，非常不灵活。

**面板位置**：新增一个轻量入口，建议放在"字段与收益相关性"面板顶部，一个 `+ 添加自定义字段` 按钮。

**交互设计**：点击后弹出一个简单表单：字段名（自定义命名）+ 公式输入框（支持基础四则运算，字段名从联想框选取插入，避免手打拼错），提交后立刻加入 `scatterOptions`，散点图/相关性表/过滤条件里都能选到它，和内置字段体验一致。

**计算逻辑**：公式解析不需要引入完整的表达式引擎，可以限定语法为"字段A 运算符 字段B"这种最简单的二元形式（覆盖用户 90% 的真实需求），用简单的字符串分割+`getFeature`取值+对应运算符计算即可；如果后续需求变复杂（比如三元运算、常数参与），再考虑引入轻量表达式解析库。

**可视化输出**：无需新图表，自定义字段和内置字段一视同仁地出现在现有各处字段选择器里；相关性表里用一个小标签区分"自定义"字段（类似现有的"原始/组装"标签），方便用户识别哪些是自己加的。

**边界情况**：自定义字段名和已有字段重名时禁止提交，并给出提示；公式里引用了不存在的字段名时提交前做校验，不允许生成一个永远算不出值的字段。这两个校验直接复用第 5 点里已有的"字段名精确匹配"校验思路（`isFilterableField` 同款逻辑）。

### 10.3 一键生成分析报告

**目标问题**：用户分析完想分享给团队时，现在只能截图拼凑，丢失了很多上下文（比如当时用的过滤条件是什么），也不方便存档回顾。

**面板位置**：全局功能，入口同样放在顶部 `app-header`，`导出报告` 按钮。

**交互设计**：点击后弹出勾选框，让用户选择要包含哪些部分（总览统计 / Top相关性 / 当前散点图 / 分箱图 / 数据质量摘要等，默认全选），选择导出格式（Markdown 或 PDF），点击生成。

**计算逻辑**：Markdown 版本直接拼接文本 + 表格（复用各面板已经算好的数据，不需要重新计算），图表部分可以用 Plotly 的 `toImage` API 导出成 base64 图片嵌入；PDF 版本可以先生成 Markdown/HTML 再走浏览器打印或者一个轻量 HTML-to-PDF 转换。

**可视化输出**：生成的报告结构建议是"过滤条件说明 → 总览统计 → 数据质量摘要 → Top相关性表 → 关键图表 → 结论区（留空给用户手动补充解读）"，最后这个"结论区"很重要——工具只负责呈现数据事实，不替用户下结论，避免暗示某种确定性判断。

**边界情况**：图表数量多、数据量大时导出耗时可能较长，需要有明确的加载态反馈（"正在生成报告，预计需要 X 秒"），避免用户以为卡死重复点击。

## 13. 自定义字段功能增强（在 10.2 基础上）

10.2 只覆盖了"最简单的二元公式"，这里是在已经上线的自定义字段能力基础上做的四点增强，重点是降低使用门槛、解决"存哪儿""怎么共享""删错了怎么办"这几个真实会遇到的问题。

### 13.1 公共函数库

**目标问题**：10.2 设计的公式语法是"字段A 运算符 字段B"这种最简形式，用户想写"避免除以0"这种稍微复杂一点的逻辑就得靠运算符硬凑，体验不好，也容易写错。

**实现要点**：在公式解析器里预置一组白名单函数，用户写公式时可以直接调用，而不是自己拼条件判断：
- `safeDiv(a, b)`：`b` 为 0 或缺失时返回 `null` 而不是 `Infinity`/`NaN`，直接替代用户重复写的 `x !== 0 ? a/b : null`。
- `pct(a, b)`：等价于 `safeDiv(a, b) * 100`，专门给"占比类"组合用，语义比裸写乘除更清楚。
- `clamp(x, min, max)`：把值限制在区间内，防止个别极端值把后续相关性/图表拉爆。
- `log1p(x)`：`log(1+x)`，给长尾分布字段（比如 mcap、volume）做压缩变换时常用，比用户自己处理"x可能是0导致log报错"的边界要省心。
- `zscore(x, field)`：直接引用某个字段在当前 `activeRows` 里的均值/标准差做标准化，复用第 3 点多元回归里已经设计好的标准化逻辑，不用用户自己算。

**交互设计**：公式输入框旁边加一个"可用函数"折叠提示（点开显示函数名+一句话说明+示例），输入函数名时联想框也把这些函数名和字段名放在一起提示（复用现有 `attachAutocomplete`，只是把候选列表从"仅字段"扩展成"字段+函数"）。

**边界情况**：函数名必须是白名单里固定的几个，不支持用户自定义函数（避免公式解析器复杂度失控，也避免出现死循环、递归引用这类风险），公式解析时如果出现未知函数名，直接在保存前拦截并提示"未识别的函数名：xxx，可用函数见上方列表"。

### 13.2 导入/导出自定义字段配置

**目标问题**：自定义字段现在只存在 `localStorage`，换浏览器、清缓存、换设备都会丢失，团队里其他人也没法直接用你调好的组合字段，只能口头描述公式让对方重新敲一遍。

**实现要点**：`导出为 JSON` 按钮把当前所有自定义字段（字段名+公式+备注）序列化成一个 JSON 文件，走现有 `downloadCsv` 同款的 Blob 下载逻辑（只是内容换成 JSON，不需要新写下载机制）；`从 JSON 导入` 走现有 `readJson`（原本用来读 calls/snapshots 的那个 FileReader 封装可以直接复用）读取文件，解析后逐个字段做校验（复用 13.1 的白名单函数校验 + 引用字段是否存在的校验）再合并进当前配置。

**交互设计**：导入时如果本地已经存在同名自定义字段，弹出选择——"覆盖" / "跳过" / "重命名后导入"（比如自动加后缀 `_imported`），避免不声不响覆盖用户自己调好的字段。

**边界情况**：导入的 JSON 如果是老版本格式（比如后续加了新的元数据字段），做一个简单的版本号字段（`"version": 1`）向后兼容检查，版本不匹配时给出"该配置文件可能来自旧版本工具，部分设置可能无法正确导入"的提示，而不是直接解析失败报错。

### 13.3 字段依赖可视化与删除保护

**目标问题**：如果自定义字段 B 的公式里引用了自定义字段 A（比如 `B = safeDiv(A, mcap)`），现在只是"按定义顺序算"，没有真正的依赖关系记录。用户删除字段 A 时，字段 B 会静默失效（算出来全是 null），但界面上不会有任何提示，用户很可能过了很久才发现某个图表突然没数据了。

**实现要点**：解析每个自定义字段的公式时，扫描其中引用到的字段名，如果引用的字段本身也是自定义字段，记录一条依赖边（A → B 表示"B 依赖 A"），维护一张轻量的依赖关系表（不需要引入图数据库，一个 `Map<字段名, Set<被谁依赖>>` 就够用）。

**交互设计**：自定义字段列表里，每个字段名旁边如果有其他字段依赖它，显示一个小图标 + 数字（比如"🔗 被2个字段依赖"），hover 显示具体是哪几个；删除操作从"直接删"改成先检测依赖，如果有依赖字段，弹出明确警告——"删除 A 后，依赖它的字段 B、C 将无法正常计算（会显示为空），是否继续？"，而不是现在这种无声无息的"删了就删了"。

**边界情况**：如果用户坚持删除，被依赖的字段不做级联自动删除（避免连锁误删），而是保留字段定义但在下次打开列表时显示"⚠️ 引用了不存在的字段：A，计算结果将为空"，给用户留出手动修复公式的机会。

### 13.4 代码模板/示例库

**目标问题**：面对一个空白的公式输入框，新用户不知道能写什么、该怎么写，上手门槛主要卡在"从0开始想公式"这一步，而不是语法本身。

**实现要点**：在自定义字段面板里放几个"示例"按钮，覆盖几类最常见的组合模式，点击直接把模板代码（带占位字段名）填进输入框，用户只需要把占位字段名换成自己想用的：
- **比率类**：`safeDiv(字段A, 字段B)` —— 示例场景"买卖比"。
- **占比类**：`pct(字段A, 字段A + 字段B)` —— 示例场景"买方占比 = 买入金额/(买入+卖出金额)"。
- **归一化类**：`zscore(字段A, 字段A)` —— 示例场景"把市值标准化后再比较不同量级的token"。
- **条件分类打标签**（这个稍微超出目前"二元公式"的范围，属于未来可以配合 8.2 的分箱能力做成"公式里可以嵌入简单的三元判断"，第一版可以先只支持数值型模板，分类打标签模板放到公式语法扩展之后再开放）。

**交互设计**：每个示例按钮下面配一行灰字小字说明"适合什么场景用"，而不是只给代码，帮用户理解"这个模板解决的是什么问题"而不只是"怎么抄"。

**边界情况**：模板填入后输入框里的占位字段名（比如"字段A"）不是合法字段，提交前的校验会自然拦下并提示替换，不需要额外设计校验逻辑，复用 13.1/13.2 已有的校验即可。

## 14. 数据源与工作流优化

### 14.1 多文件批量分析 / 追加数据

**目标问题**：现在每次点"分析"是全量替换 `matchedRows`。如果用户按天导出多批 calls/snapshots 文件，想合并成一个更大的分析集，现在只能一次性喂一个巨大的合并文件进去（手动合并容易出错），没法在工具里直接"追加"。

**实现要点**：文件选择改成支持多选（`<input type="file" multiple>`），或者在现有"分析"按钮旁加一个"追加数据"按钮（区别于"分析"是覆盖，"追加"是合并进当前 `matchedRows`）；合并时按 `token_address + swap_begin_time`（复用现有 `callKey`）去重，重复的记录默认"保留后导入的版本"（因为后导入的通常是更新的数据），也可以给用户一个选项"保留先导入的版本"。

**交互设计**：追加完成后的提示要明确写清楚"新增 X 条，去重覆盖 Y 条，当前工作集共 Z 条"，让用户清楚知道合并的实际效果，而不是只显示一个模糊的总数。

**边界情况**：多批文件如果字段结构不完全一致（比如后面导出的文件多了几个新字段），`allNumericKeys` 需要在每次追加后重新计算合并（现有逻辑本来就是遍历 `matchedRows` 生成，天然兼容，不需要额外处理）；但要注意如果老数据里没有新字段，这些记录在新字段上是"缺失"而不是"0"，需要确认 `getFeature` 对不存在的 key 返回 `undefined` 而不是誤转成 0（现有代码已经是这样，只需要在追加逻辑里保持一致，不要图省事给缺失字段填默认值）。

### 14.2 分析结果持久化 / 多数据集切换

**目标问题**：这一点和第 10.1 节已经设计的"分析快照保存/对比"目标相近但不完全一样——10.1 存的是"分析结果摘要"（过滤条件+相关性Top N），用来做"轻量对比两次分析的结论差异"；这里用户想要的是**保存/切换完整的原始工作集**（比如"昨天的 100 条 vs 今天的 100 条"整体切换着看），是更"重"的数据持久化需求，两者应该是同一套存储机制下的两种粒度，而不是重新设计一遍。

**实现要点**：复用 10.1 已经设计好的 `window.storage` 持久化方案，但增加一种"数据集快照"类型（区别于"分析结果快照"）：保存时把当前 `matchedRows`（含自定义字段计算结果）整体序列化存储，命名后加入一个"数据集"下拉选择器；切换数据集时相当于重新执行一次"分析"，只是数据来源从"重新读取上传文件"变成"从存储读取"。

**交互设计**：顶部 `app-header` 增加一个数据集切换下拉（和 10.1 的"快照列表"入口相邻，作为同一个存储体系的两个视图，UI 上不要让用户困惑这是两套不同的东西）。

**边界情况**：`matchedRows` 数据量大时，直接整体存进 `window.storage`（有 5MB/key 的限制）可能超限，需要做体积检测，超过阈值时提示"数据集过大无法完整保存，建议只保存分析结果摘要（见快捷键/入口）"，引导用户退回到 10.1 更轻量的方案。

### 14.3 大数据量处理进度反馈

**目标问题**：`buildRows` 现在是同步的 for 循环，如果 snapshots 有几万条，遍历+特征展开会让主线程长时间被占用，页面表现为"卡死无响应"，用户不知道是真的卡死了还是在算，容易误操作重复点击。

**实现要点**：把 `buildRows` 的主循环拆成分批处理，每处理一批（比如 500 条）就让出一次主线程（用 `setTimeout(fn, 0)` 或者更平滑的 `requestAnimationFrame` 循环调度），每批处理完更新一次进度状态，驱动一个简单的进度条/文字提示重新渲染。如果后续数据量进一步增长（十万级以上），可以考虑挪到 Web Worker 里算（彻底不占用主线程），但作为第一步，分批+让出主线程的改动成本最低，能解决"卡死无反馈"这个最影响体验的问题。

**交互设计**：分析按钮点击后，原来的"分析中..."文字状态升级成带百分比的进度条（"正在处理 12,000 / 45,000 条记录（27%）"），处理耗时较长时用户至少知道系统在正常工作，而不是怀疑卡死了要刷新页面重来。

**边界情况**：分批处理期间用户如果再次点击"分析"按钮（比如重新选了文件），需要有一个"取消上次分析"的机制（一个简单的标志位，分批循环每次检查该标志位，为真就提前退出），避免两次分析的结果互相污染。

## 15. 可用性与交互优化

### 15.1 过滤条件保存为"预设方案"

**目标问题**：常用的过滤条件组合（比如"低风险信号：bundler占比<10% AND top10持仓<30%"）现在每次都要重新拼几行条件，效率低，也容易漏填某一行导致结果不一致。

**实现要点**：复用自定义字段（10.2/13.2）已经设计的持久化+导入导出机制——过滤条件方案本质上也是"一组结构化配置存起来，随时应用"，实现上可以共用同一个存储命名空间下的不同 key 前缀（比如 `customField:xxx` 和 `filterPreset:xxx`），不需要另起一套存储逻辑。

**交互设计**：现有"全局条件过滤"面板的按钮行（添加条件/筛选CA/复制CA/清除）旁边加"保存为预设" + 一个预设下拉选择器；保存时把当前 `#filterRows` 里所有有效条件行序列化，应用时清空现有条件行后按方案重建（复用现有 `addFilterRow(field, op, threshold)` 的参数化调用方式，本来就是为这个场景设计的，不需要改动）。

**边界情况**：预设方案里的字段名如果在当前数据集里不存在（比如换了一批字段结构不同的数据），应用时按 13.2 同款的校验逻辑跳过无效字段行并给出提示，而不是应用一半报错中断。

### 15.2 散点图批量操作

**目标问题**：X 指标多选之后可能同时展开 10+ 张散点图，现有的对数轴/置信区间/分档统计等开关都是每张图单独设置（`getChartSettings(xField)` 按字段分别存储），用户想统一开启某个选项时得逐张点，尤其在批量探索阶段很低效。

**实现要点**：在"散点图分析"面板顶部（绘图按钮旁）加一排"批量操作"按钮：`全部启用对数X` / `全部启用置信区间` / `全部启用分档统计` / `重置全部为默认`，点击后遍历 `chartSettings`（现有的 `Map<xField, settings>`）批量更新对应字段，然后统一调用一次 `plot()` 重新渲染，而不是每张图单独触发重渲染（减少不必要的重复计算）。

**交互设计**：批量按钮不做"开关"语义（不做成 toggle），而是明确的"设为开启"动作，避免用户搞不清当前是批量操作前的状态还是操作后的状态；如果需要批量关闭，提供对应的"全部关闭XX"按钮或者"重置为默认"统一入口。

**边界情况**：批量操作只影响"当前已经展示的图表"对应的字段设置，不影响用户后续新增 X 指标时的默认值（新增图表还是从 `getChartSettings` 的默认值开始），除非用户额外要求"新增图表也沿用当前批量设置"，这个可以作为二期增强，第一版明确"批量操作只作用于当前已存在的图表"即可，避免语义模糊。

### 15.3 CSV 导出跟随当前过滤 / 自定义字段

**目标问题**：现有 `downloadCsv` 有两个问题：① 固定导出全量 `matchedRows`，用户设置了全局过滤想导出的往往是过滤后的子集，现在做不到；② `featureKeys` 是从 `matchedRows.flatMap(r => Object.keys(r.features))` 反推出来的，如果某个自定义字段的计算结果对所有行都恰好是 `null`（比如公式写错了，或者依赖的字段普遍缺失），这个字段可能压根不会出现在任何一行的 `r.features` 里，导致导出的 CSV 直接漏掉这一列，用户不会意识到这个字段"存在但没算出来"和"根本没导出"是两回事。

**实现要点**：
- 导出前加一个单选/开关："导出当前过滤后的数据（`activeRows`）" vs "导出全部数据（`matchedRows`）"，默认选中前者（更符合"导出我正在看的这份结果"的直觉）。
- 列集合不再从 `matchedRows` 的行数据反推，而是从**字段注册表**（`scatterOptions` 并入所有已注册的自定义字段名，无论其计算结果是否为空）里取全集，即使某自定义字段全员为空，也要在 CSV 里出现这一列（值留空），保证"字段存在"和"字段有值"这两件事在导出结果里能被区分开来。

**边界情况**：导出的文件名建议把当前是否过滤、导出的行数带上（比如 `returns_features_filtered_42rows.csv`），方便用户事后从文件名就能分辨这份导出对应的是哪种口径，避免几次导出后自己也搞混。

### 15.4 图表导出为图片

**目标问题**：用户想把某张散点图/分箱柱状图贴进分析报告或者分享给同事，现在只能截图，分辨率和裁剪都不理想。

**实现要点**：Plotly 本身自带 `Plotly.downloadImage` / `toImage` API，不需要自己实现导出逻辑，只需要在每张图的 `.chart-controls` 工具栏里（复用现有散点图卡片的按钮行样式）加一个"导出 PNG"按钮，调用该 API 并传入当前图表的 DOM 节点即可。

**交互设计**：导出时用当前图表标题（`titleText.textContent`，现有变量）作为默认文件名，避免用户拿到一堆"newplot.png"分不清是哪张图；同时设置导出分辨率为屏幕分辨率的 2 倍（`scale: 2`），保证贴进文档里不糊。

**边界情况**：深色主题下导出的图片背景是深色的，如果用户要贴到白底的文档/PPT 里会不协调，可以在导出按钮旁加一个小选项"导出时使用浅色背景"（临时用浅色 `darkLayout` 参数渲染一份用于导出，不影响页面上实际展示的深色图表）。

## 16. 健壮性 / 工程化（长期考虑）

这一节不是新增用户可见的功能，而是保证前面所有功能能持续、稳定地叠加下去的工程基础。建议在功能数量明显增多（比如做完本文档里 P0/P1 级别的功能之后）就要开始投入，而不是无限往后拖——单文件行数越涨，后续每加一个功能的边际成本越高。

### 16.1 拆分单文件

**现状问题**：`chart.html` 目前把 CSS/HTML/JS 全部塞在一个文件里，且已经涨到 2600+ 行；本文档设计的十几个新功能全部实现后，预计会再增加数千行，单文件会变得很难在编辑器里定位代码、也难以进行局部测试。

**拆分建议**（按职责边界拆，而不是按行数机械切分）：
- `data.js`：纯数据处理层——`flattenObject`/`flattenCtx`/`buildRows`/`num`/`isAddressLikeKey` 这类不依赖 DOM 的函数，理论上可以脱离浏览器环境独立运行（这点很重要，直接关系到 16.2 能不能顺利做单元测试）。
- `stats.js`：统计计算层——`pearson`/`linearRegression`/`percentile`/`tukeyFence`/`pearsonPValue` 等纯数学函数，同样不依赖 DOM。
- `customFields.js`：13.1-13.4 设计的自定义字段解析、校验、依赖分析、导入导出逻辑，是一个相对独立的子系统，值得单独成文件。
- `charts.js`：所有 Plotly 渲染相关函数（`darkLayout`/`renderScatterChart`/`renderBinBarChart` 等），依赖 DOM 但逻辑上和数据计算是分离的。
- `ui.js`：事件绑定、面板折叠展开、`attachAutocomplete`、过滤条件行的增删改这类纯交互逻辑。
- `main.js`：入口文件，负责把各模块串起来、绑定顶层事件监听。

拆分后用普通的 `<script src="./xxx.js">` 顺序引入即可（工具的定位是"单文件可离线打开"的轻量工具，暂时不建议引入构建工具/打包器，除非未来要做 npm 包发布或者接入 TypeScript，那是更大的决策，本文档先不展开）。

**边界情况**：拆分过程中最容易出问题的是全局变量的隐式依赖（比如 `matchedRows`/`activeRows` 这些模块级变量目前被到处直接读写），建议拆分时顺手把这些变量收进一个统一的 `AppState` 对象里显式传递，而不是继续依赖"反正都在同一个 `<script>` 作用域里"这种隐式耦合，否则拆完文件之后这些跨模块的全局状态反而更难追踪。

### 16.2 单元测试覆盖核心计算

**现状问题**：这次修复"空字符串被误判为 0"、"0x地址被解析成数字"这类 bug，都是靠人工审读代码发现的。这类问题的共同特点是——纯函数、逻辑不复杂，但一旦有回归很难靠肉眼在几千行代码里再次发现，靠"人工再审一遍"不是可持续的质量保证方式。

**实现要点**：16.1 完成模块拆分后，`data.js`/`stats.js`/`customFields.js` 里的函数大多是不依赖 DOM 的纯函数（输入输出明确），非常适合用 Node.js 直接跑测试（不需要启动浏览器/headless browser，跑得快、CI 里也容易接入）。优先覆盖的函数清单：
- `flattenObject`/`flattenCtx`：给几个精心构造的边界输入（空字符串字段、0x地址字符串、嵌套对象、百分比字段）断言输出符合预期，这次修的几个 bug 都应该变成对应的测试用例，防止未来重构时再次踩坑。
- `buildRows`：构造几组 calls+snapshots 的最小样例（含"时间差超过阈值应被跳过""市值为0应被过滤"这类边界场景），断言匹配结果。
- `pearson`/`linearRegression`：用已知解析解的简单数据集（比如完全线性相关的构造数据）验证计算结果。
- `compileCustomField`（13.x 新增的自定义字段公式解析器）：断言合法公式能正确求值、非法字段名/函数名能被正确拦截，这是这次新增功能里最适合"写一个测试就能省很多手工验证时间"的模块。

**边界情况**：暂时不需要引入完整的测试框架（Jest/Vitest 这类），如果想保持"轻量单文件工具"的定位，用 Node 自带的 `node:assert` + 一个简单的测试跑批脚本就足够覆盖这些纯函数，等模块拆分和测试规模都上来了，再考虑引入正式测试框架不迟。

### 16.3 大数据量性能优化

**现状问题**：`getFieldDesc`/`isNumericColumn` 这类函数目前是每次调用都做一遍 O(n) 的字符串匹配或全表扫描，而它们又被表格渲染（相关性表、字段质量表等）在循环里频繁调用，数据量和字段数一旦上涨（比如追加数据功能上线后单个工作集涨到几万行、几百个字段），页面渲染会明显变卡。

**实现要点**：
- `getFieldDesc(field)`：输入字段名到输出中文含义是一个纯函数（相同输入永远得到相同输出），且 `FIELD_DESC`/`TERM_MAP` 在运行期间不会变化，非常适合加一层简单的 `Map` 缓存（`fieldDescCache.has(field) ? cache.get(field) : 计算并存入cache`），一次计算、多次复用。
- `isNumericColumn(col)`：现在是每次调用都重新遍历一遍 `matchedRows` 检查该列是否全部可转数字，但这个结果只有在 `matchedRows` 本身变化（重新分析/追加数据）时才会变，可以在 `updateScatterSelects()` 阶段一次性算好存进一个 `Map<字段名, boolean>`，后续直接查表，不用每次都重新扫全表。

**边界情况**：加缓存最大的风险是"数据变了但缓存没失效"，需要明确规定缓存的失效时机——`matchedRows` 被重新赋值（新分析/追加数据完成）时统一清空这两个缓存，而不是散落在各处零散清理，否则容易漏清导致显示的是过期数据算出来的结果。

## 17. 二~五类新增项的优先级建议

沿用第 11 节的排期思路，但这几类大多不是"用户可感知的新分析能力"，而是对已有功能的打磨或工程基础，优先级判断标准也略有不同——这里更看重"改动小、直接解决当前真实存在的问题"排在前面。

| 优先级 | 功能 | 类别 | 复杂度 | 理由 |
|---|---|---|---|---|
| P0 | CSV导出跟随过滤/自定义字段（15.3） | 可用性 | 低 | 是一个明确存在的数据缺陷（自定义字段可能漏列），不是"锦上添花"，应该优先修 |
| P0 | 大数据量处理进度反馈（14.3） | 数据源工作流 | 低-中 | 分批+让出主线程改动集中在 `buildRows` 一个函数内，直接解决"卡死无反馈"这个最影响体验的问题 |
| P0 | 公共函数库（13.1） | 自定义字段 | 低 | 只是给公式解析器加几个预置函数，改动集中，能显著降低自定义字段的上手门槛 |
| P1 | 字段依赖可视化与删除保护（13.3） | 自定义字段 | 中 | 依赖关系表的维护逻辑不复杂，但要覆盖"删除时警告""引用不存在字段时提示"这几个交互细节 |
| P1 | 导入/导出自定义字段配置（13.2） | 自定义字段 | 低-中 | 可以直接复用现有 `readJson`/下载逻辑，主要工作量在校验和冲突处理（同名字段怎么办） |
| P1 | 过滤条件预设方案（15.1） | 可用性 | 低-中 | 和 13.2 共用同一套持久化+导入导出机制，两个功能可以打包一起做 |
| P1 | 拆分单文件（16.1） | 工程化 | 中 | 越往后功能越多，拆分成本会越来越高，建议在功能数量明显增多前就动手，不要无限期往后拖 |

## 18. 分析方法论增强（统计陷阱防护 + 决策落地能力）

前面 1-17 节设计的功能本质上都是"用历史数据描述历史数据"——算相关性、算分布、算分组差异，但没有回答几个更根本的方法论问题：这些结论会不会是巧合？会不会是统计假象？能不能直接支持一个买/不买的决策？这一节补上这几类能力。

> **范围说明**："风险调整后收益 / 资金曲线模拟"（夏普比率、真实回测账户曲线）经确认**不纳入本文档设计**，原因是当前数据结构不支持——缺少真实下单时间序列、仓位规模、并发持仓上限这类交易约束信息，7.2 节的"累计收益曲线"已经是在现有数据条件下能做到的最接近的近似（等权重简化版），如果未来数据层面补上完整的模拟交易记录，这块可以作为独立需求另起一份设计。

### 18.1 样本外验证 / 过拟合检测

**目标问题**：现在所有相关性、回归系数、分箱阈值都是"在同一批数据上算、在同一批数据上看结果"，这是纯粹的样本内（in-sample）分析。字段数量一多（尤其是 8.3 特征交互探索会批量生成几百个候选组合），纯属巧合撞上"看起来显著"的字段概率会明显上升，用户很容易把噪声当信号。

**面板位置**：不新增独立面板，而是在"字段与收益相关性""相关性矩阵""多元回归"这几个已有面板顶部统一加一个开关：`启用样本外验证`，这样验证能力覆盖所有下游相关性分析，而不是只做一个孤立的新功能。

**交互设计**：开关打开后出现两个附加选项——切分方式（`按时间顺序切分（推荐）` / `随机切分`，时间序列数据用随机切分容易泄露未来信息，默认选时间顺序）+ 切分比例滑块（默认训练 70% / 测试 30%）。

**计算逻辑**：按 `swap_begin_time` 排序后取前 70% 作为训练集、后 30% 作为测试集（随机切分模式则直接洗牌 `activeRows` 后按比例切）。相关性表在训练集上跑一遍 `computeCorrelations`，同时对测试集也跑一遍，两组结果并排展示；回归模块则更严格——用训练集拟合出的标准化系数、均值、标准差，直接应用到测试集上做预测，计算样本外 R²（预测值和真实值的相关性平方），而不是在测试集上重新拟合一套新系数（重新拟合就失去了"验证"的意义）。

**可视化输出**：相关性表新增"训练集 r"和"测试集 r"两列（替代原来单一的"r"列），衰减幅度较大的行（比如测试集 |r| 相比训练集下降超过 50%，或者符号发生翻转）用醒目颜色标出并加提示"该字段的相关性在样本外明显减弱，可能是过拟合/巧合，谨慎作为决策依据"。回归模块展示"训练集 R²"和"测试集 R²"对照，两者差距过大时同样给出过拟合警告。

**边界情况**：`activeRows` 总量较小（比如全局过滤后只剩几十条）时，切分后测试集样本量可能不足以得出稳定结论，需要在测试集 n < 20 时明确标注"测试集样本过少，验证结果仅供参考"，而不是假装这个验证是可靠的。

### 18.2 多重比较校正

**目标问题**：相关性表一次性展示几十上百个字段的 p 值，但从没做过多重检验校正。统计学基本事实：同时测试 100 个和结果毫无关系的字段，纯靠运气也会有约 5 个显示"p<0.05 显著"（这就是"显著性水平 α=0.05"的定义本身）。现有的 p 值列会系统性高估"真正显著"的字段数量。

**面板位置**：直接扩展现有"字段与收益相关性"表，不新增面板——新增一列"校正后 p 值（FDR）"，改动成本很低但价值很高。

**交互设计**：表格上方加一个校正方法下拉（`Benjamini-Hochberg FDR（推荐，较宽松）` / `Bonferroni（更保守）`），以及一句自动生成的对比摘要，比如"未校正时有 18 个字段 p<0.05，多重比较校正后仅剩 6 个仍然显著"，用一句话把校正的实际影响讲清楚，而不是让用户自己数表格。

**计算逻辑**：**关键细节**——校正用的检验总数 `m` 必须是**该目标（returnCurrent/returnMax）下参与检验的全部字段数**（即 `allCorrelations` 里对应 target 的完整条目数），而不是当前 `topN` 截断后展示的数量，否则会系统性低估需要校正的严重程度。
- Bonferroni：`p_corrected = min(1, p_raw × m)`，实现最简单但偏保守。
- BH-FDR（推荐默认）：把 m 个 p 值升序排列，找到最大的 k 满足 `p(k) ≤ (k/m) × α`，第 1 到第 k 个视为显著；q 值（校正后可比较的量）用标准的"从最大 p 值往回取累计最小值"算法得到，复用现有 `percentile`/排序类工具函数即可，不需要引入统计库。

**可视化输出**：原来的显著性判断（比如高亮 p<0.05 的行）改成基于校正后的结果；被"校正掉"的行（原本 p<0.05，校正后不再显著）用浅灰色+删除线样式区分，而不是直接从表格里消失——让用户看到"曾经以为显著、其实经不起多重比较校验"的字段，这本身就是重要信息。

**边界情况**：`corrSource`/`corrTarget` 筛选器切换时，m 的计算范围要跟着筛选器变化（比如只看"组装字段"时 m 应该是组装字段的数量，不是全部字段），否则校正力度和用户实际看到的假设检验范围对不上。

### 18.3 基准对照组（随机采样 Baseline）

**目标问题**："胜率 60%"这个数字没有参照系——相对完全不做任何筛选、随便选 token，60% 算好还是差？现在的工具完全没有对照组的概念，容易把"赶上了普涨行情"误判成"策略真的有效"。

**面板位置**：新面板 `基准对照分析`，放在"总览统计"旁边，作为它的直接延伸。

> **重要的数据依赖说明（如实告知）**：这个功能能不能做，取决于数据源的构成。如果 `snapshots` 文件里只包含"已经被策略筛中触发过信号"的 token（当前数据结构看起来正是这种情况——每条记录都挂在一个 `strategy_id` 下面），那么在这份数据内部做的"随机抽样基准"，本质上只是"策略内部信号的随机重排对照"，并**不能**回答"这个策略相比完全不筛选的效果如何"这个更本质的问题。要做到真正有意义的基准对照，需要额外一份"未经策略筛选的全量 token 快照池"作为随机抽样的母体——这是一个数据层面的前提条件，如果拿不到，这个面板应该显式提示用户"当前数据仅包含已触发信号的 token，无法构建真正的随机基准；如需该分析，请提供未筛选的全量快照数据"，而不是拿现有数据凑一个看似合理、实则文不对题的"伪基准"。

**交互设计**（假设前提数据可用）：`生成随机基准` 按钮 + 重抽样次数设置（默认 1000 次）；如果数据源不满足前提条件，按钮直接置灰并显示上面那段说明，不允许用户在数据不支持的情况下强行生成一个误导性结果。

**计算逻辑**：从全量未筛选 token 池里，每次随机抽取和当前策略样本量相同的 N 个 token，计算这组随机样本的胜率/平均倍数，重复 1000 次，得到基准指标的经验分布；把策略实际表现（真实胜率/均值）在这个分布里定位百分位（比如"策略实际胜率落在随机基准分布的第 97 百分位"），这本质上是一个非参数的显著性检验，不需要假设正态分布。

**可视化输出**：直方图展示 1000 次随机抽样得到的胜率/均值分布，一条竖线标出策略实际表现所在位置，配一句自动生成的结论，比如"策略实际胜率超过了 97% 的随机抽样基准，在统计意义上具有正向 alpha"；如果策略表现落在基准分布中段（比如 40-60 百分位），明确提示"策略表现和随机选择没有显著差异，当前样本下未能证明该策略具有超额收益"，说真话而不是选择性只展示好看的一面。

**边界情况**：见上方数据依赖说明——这是本功能最大的边界情况，其余边界情况（重抽样次数、计算耗时）参考 18.4 Bootstrap 部分的处理方式即可，不重复展开。

### 18.4 相关性系数置信区间（Bootstrap）

**目标问题**：现有 p 值（`pearsonPValue`，基于 Fisher z 变换的正态近似）只回答"这个相关性是否显著不为 0"，不回答"这个 r 值本身有多稳"。一个 r=0.4 但换一批数据可能变成 0.1 甚至变号的字段，和一个 r=0.4 且非常稳定的字段，在现有表格里看起来完全一样，这是有风险的。

**面板位置**：扩展现有"字段与收益相关性"表，新增一列"r 的 95% 置信区间"。

**交互设计**：由于 Bootstrap 计算量比普通相关性大不少（每个字段要重复抽样几百次），不做成默认自动计算（避免拖慢现有表格的默认响应速度），改成一个独立按钮 `计算置信区间`，重抽样次数可调（默认 500 次，兼顾速度和精度，字段多时给出预计耗时提示，复用 14.3 设计的分批处理思路，避免大量重抽样计算卡住主线程）。

**计算逻辑**：对每个字段，从该字段与目标收益的 (x, y) 数据对里做**有放回**重抽样（抽样规模等于原始 n），重复 B 次（默认 500），每次重新调用现有 `pearson()` 计算 r，得到 r 的经验分布，用现有 `percentile()` 函数取第 2.5% 和 97.5% 分位数作为 95% 置信区间，不需要引入新的统计库。

**可视化输出**：表格新增"置信区间"列，格式如 `[0.05, 0.72]`；**区间跨越 0 的行**（比如 `[-0.10, 0.35]`，即使点估计 r 看起来不小）用特殊颜色标出并提示"置信区间跨零，不能排除该字段与收益实际无关的可能，点估计值可能只是运气"——这类信息比单看 p 值列更直观，能直接防止用户"重仓一个看起来强、实际上极不稳定的信号"。

**边界情况**：n 较小（比如 < 20）时 Bootstrap 本身的估计也不稳定，建议在样本量过小时给出"样本量过小，置信区间估计本身可信度有限，仅供参考"的提示，而不是呈现一个看似精确、实则同样脆弱的区间数字。

### 18.5 阈值优化 / ROC-AUC 分析

**目标问题**：现在筛选阈值全靠用户手填，或者靠 8.2 简化版决策树推荐单个分裂点。但如果最终目标是"用这个字段做一个买/不买的二分类筛选条件"，更贴合场景的工具是 ROC 曲线和 AUC——它直接回答"这个字段能不能把赢家和输家分开"，以及"分界点定在哪里精确率/召回率最优"，比相关系数更直接服务于决策落地。

**面板位置**：新面板 `阈值优化（ROC 分析）`，放在"分箱柱状图"和"分类字段对比"附近（同属"支持具体筛选决策"的功能组）。

**交互设计**：选择候选数值字段（可单选深入分析，也可多选批量对比）；盈利判定阈值可调（默认 `returnCurrent > 1`，也支持改成"翻倍才算赢"这类更严格的标准）；方向选择"字段越大越可能盈利" / "字段越小越可能盈利" / 自动检测（按算出来的 AUC 是否 > 0.5 自动判断，AUC < 0.5 说明方向反了，直接取 1-AUC 并翻转方向提示用户）。

**计算逻辑**：把目标收益转成二分类标签（赢/输），对候选字段的每个候选切点（取该字段全部唯一值作为候选，唯一值过多时按分位数降采样到比如 100 个候选点以控制计算量），计算该切点下的真阳性率（TPR）和假阳性率（FPR），连成 ROC 曲线；用梯形法则对曲线下面积做数值积分得到 AUC；额外计算 Youden's J 统计量（`TPR - FPR` 最大化）对应的切点，作为"综合来看最优"的推荐阈值。

**可视化输出**：ROC 曲线图（Plotly 折线），叠加对角虚线标出"随机猜测"基准（AUC=0.5）；在曲线上标出 Youden 最优点，旁边显示该点对应的具体字段阈值、精确率、召回率；一句自动生成的结论，比如"该字段 AUC=0.72，作为筛选条件时建议阈值设为 X，此时能筛出 68% 的赢家，同时误筛入 22% 的输家"。同时支持对相关性表 Top N 字段批量算 AUC，汇总成一张排序表——这是专门针对"二分类决策场景"的排序依据，和相关性排序是互补而非替代关系，值得在文案上和相关性表做一下区分说明，避免用户混淆两种排序的适用场景。

**边界情况**：连续型字段（比如 `mcap`）唯一值可能有几百上千个，全量候选切点计算量较大，用分位数降采样（比如只在 100 个分位点上取候选切点）不会明显影响 ROC 曲线的整体形状，但能大幅降低计算量，这个降采样策略应该作为默认行为而不是可选项。

### 18.6 持有期优化分析

**目标问题**：数据里已经有 `max_up_duration`（从开仓到最大涨幅的耗时）这类字段，但没有分析工具把它用起来回答"这个信号应该拿多久"，现在的分析视角完全是静态的（只看"最终有没有超过某个倍数"），没有时间维度上的持有期优化。

**面板位置**：新面板 `持有期分析`，放在"时间维度分析"附近。

> **数据完整性说明（如实告知，和第 3 点被排除的原因类似）**：这个功能能做到什么精细程度，取决于每条快照是否带有完整的价格时间序列。当前数据结构里 `ctx.kline_and_indicators.kline_bars` 理论上能提供这个信息，但从你之前给的真实样例数据看，这个字段在大多数快照里是空数组 `[]`——如果实际数据集里这个字段普遍为空，"持有 X 分钟后卖出能拿到多少收益"这种连续型模拟是做不出来的，只能退化成基于"开仓价 / 当前价 / 历史最高价"这三个离散锚点的粗略线性插值估算，且必须在图表上明确标注"插值估算，非真实价格路径"，不能包装成精确回测结果误导用户。

**交互设计**：面板打开时先检测当前数据集里 `kline_bars` 的非空覆盖率（复用第 6.1 节已设计的字段覆盖率检测逻辑），覆盖率高时启用"增强版"（下方描述），覆盖率低或为 0 时自动降级为"简化版"并显示上面的说明文字，不需要用户手动选择。

**计算逻辑（简化版，多数情况下会用到这个）**：基于 `signal_open_mcap`（起点）、`current_mcap`（当前，近似终点）、`signal_max_mcap` + `max_up_duration`（最高点及其耗时）这三个锚点，做分段线性插值，估算"耗时达到 max_up_duration 的 X%（比如 25%/50%/75%）时，市值大概是多少"，进而估算收益倍数；按信号类型或整体聚合出"持有耗时百分位 vs 平均收益倍数"的曲线。

**计算逻辑（增强版，仅当 `kline_bars` 数据完整时可用）**：直接用真实 K 线数据，对每个信号计算"任意持有时长对应的实际市值"，不需要插值近似，可以标出真正意义上的"最优退出时间窗口"（收益/时间的边际增益开始下降的拐点）。

**可视化输出**：简化版——一条"持有耗时分位点 vs 平均估算收益倍数"折线图，标题和图注反复强调"插值估算"字样，避免被当成精确回测；增强版——更精细的持有时长-收益曲线，可以标出统计意义上的最优退出窗口区间。

**边界情况**：如果 `kline_bars` 覆盖率处于中间状态（比如 30% 的记录有完整 K 线，其余没有），增强版分析应该只用有完整数据的那个子集计算（而不是混用插值和真实数据拉低精度），并在图上明确标注"该分析基于 X 条有完整价格数据的样本（占当前工作集 Y%）"，让用户知道结论的样本基础有多大。

| P0 | 多重比较校正（18.2） | 低 | 只是给现有相关性表加一列+一个下拉，改动成本很低，但对结论可信度的提升是这一批里最大的，应该优先做 |
| P1 | 样本外验证（18.1） | 中 | 需要给多个已有面板加统一开关，工作量比 18.2 大，但和 18.2 一起构成"防止过拟合和假阳性"的核心组合，建议紧随其后 |
| P1 | ROC-AUC 分析（18.5） | 中 | 新面板但计算逻辑自成一体（不依赖前面的分组聚合等框架），可以独立并行开发，直接服务于"能不能拿这个字段做筛选决策"这个高频真实需求 |
| P2 | 相关性置信区间 Bootstrap（18.4） | 中-高 | 计算量比前面几项都大，需要配合 14.3 的分批处理思路一起做，建议放在那部分工程能力就绪之后再排期 |
| P2 | 基准对照组（18.3） | 中（但有数据前提） | 计算本身不复杂，但**强依赖一份当前可能拿不到的"全量未筛选快照"数据**，建议先确认数据源能不能提供，拿不到就先做"面板存在但功能置灰+说明"的最小版本，不要为了做而做出一个文不对题的伪基准 |
| P3 | 持有期优化分析（18.6） | 中（简化版）/ 高（增强版） | 和第 3 点类似受限于数据完整性（`kline_bars` 覆盖率），建议先做简化版插值估算并保留清晰的局限性说明，增强版等数据采集补全 K 线数据后再考虑 |
