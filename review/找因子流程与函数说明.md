# 找因子（Factor Lab）流程与关键函数说明

> 面向代码：`src/lib/factorLab.js`、`src/lib/auc.js`、`src/lib/factorExclusions.js`、
> `src/lib/fieldAudit.js`、`src/ui/factorLab/*`、`src/ui/FactorLab.jsx`。
> 目标：把"点扫描 → 拿到推荐因子"这条链路走一遍，并列出每个关键函数的输入输出，
> 供后续改动前快速定位，不用重新翻代码。
> 当前生效口径见 [readme.md](readme.md)：候选边际贡献评估 / 因子推荐贪心 / 配权三步
> 已"大回退"统一用**全程 ρ**（`scorePoolRho`），分层秩相关（BucketRho）/分层增益（TierGain）
> 代码保留但 UI 未接。

**兜底路径（图上没画，但每一层都有）**：`typeof Worker === 'undefined'`（SSR/测试环境）或 worker 构造抛错时，
③⑩ 两处都退回主线程串行——扫描退回 `scanFactorCandidates`（`computeFieldRaw` 循环 + 每 20 字段让出一帧 +
同一个 `assembleCampScan`），评估退回直接调 `computeHeldOutDeltaRho`，⑮ 退回直接调 `recommendFactorPool`，
⑩' 退回直接调 `permutationNullMarginalRho`。串行与并行结果必须逐字段一致，`factorlab.test.js` 有用例守着这份等价性。

## 2. 主线程 vs Worker 分工

- **三套独立 worker 池**（后两套共用 `recommendWorker.js`，只是切法不同）：
  - 扫描池（`scanCandidatesWithWorkers` + `scanWorker.js`）：只跑 `computeFieldRaw`，逐字段互不依赖，无 BH 校正。
  - 评估/推荐池（`evaluateCandidatesWithWorkers` / `runRecommendInWorker`）：按**候选**切批跑
    `computeHeldOutDeltaRho`，或单 worker 跑完整条推荐 `recommendFactorPool`（内部调 `recommendFactorPath` 做贪心）。
  - 置换零分布池（`runPermutationNullWithWorkers`，2026-07-29 新增）：按**置换次数**切片（不是切候选——
    每次置换要重打乱一遍全表 `returnMax`，只有按置换切才能让每个 worker 各自独立跑完整轮），
    各片跑 `permutationNullMarginalRho`，主线程用 `summarizeNullDistribution` 合并分位数。
- **BH 多重比较校正必须在主线程做**（`assembleCampScan`），因为要等全量字段汇总后才能校正，不能分批各做各的。
- **`rows` 只在每个 worker 建好时 `{type:'init', rows}` 发一次并缓存**，后续批次消息不再带 `rows`——
  这是 2026-07-28 修的一个真实性能坑：逐批带 rows 会把大数组结构化克隆几十上百遍，克隆发生在
  **发送方主线程**，曾把主线程 FPS 冻到 1。
- 无 `Worker`（SSR/测试环境）或 worker 构造失败时，各处都有主线程串行/直算兜底，保证结果一致
  （`typeof Worker === 'undefined'` 判断 + try/catch）。

## 3. 关键函数输入输出

### 3.1 `src/lib/factorLab.js`（核心算法库，纯函数）

#### 区间挖掘 / 打分

| 函数 | 输入 | 输出 | 角色 |
|---|---|---|---|
| `findHotInterval(rows, field, opts)` | `rows`, `field:string`, `opts:{winThreshold}` | `{lo,hi,n,pos,winRate,lift,coverage,wilsonLo,score,pPermutation,...}` 或 `{error}` | 勇者阵营：挖"高倍盘集中区"（加分区间） |
| `findColdInterval(rows, field, opts)` | 同上 | 同上 | 邪恶阵营：挖"输家集中区"（减分区间，标签取反） |
| `trapScore(x, lo0, lo1, hi1, hi0)` | 数值 `x` + 四个边界（可 ±Infinity） | `number`（0~1） | 所有打分/回测/策略代码生成公用的梯形打分函数 |
| `deriveTrapezoid(rows, field, interval, winThreshold)` | `rows`,`field`,`interval:{lo,hi}`,`winThreshold` | `{lo0,lo1,hi1,hi0}` 或 `{error}` | 满分核＝区间内目标类 P25~P75，硬界＝区间外扩10% |
| `deriveColdTrapezoid(...)` | 同上 | 同上 | 邪恶阵营版本 |
| `missingRate(rows, field)` | `rows`,`field` | `number`（0~1） | 缺失率 |

#### 全字段扫描（可并行的关键三层）

| 函数 | 输入 | 输出 | 角色 |
|---|---|---|---|
| `computeFieldRaw(rows, field, opts)` | `rows`,`field`,`opts:{winThreshold,bootstrapB,minCoverage,camp}` | `{field,auc,interval,missRate}` | **纯计算、无BH、无跨字段依赖**——可安全丢进 worker 并行，`scanWorker.js` 逐字段调它 |
| `assembleCampScan(rawList, camp)` | `rawList: computeFieldRaw结果[]`,`camp` | `{candidates:Candidate[], skipped:[{field,reason}]}` | 全量汇齐后做 AUC/区间的 BH 校正+排序，是串行/并行两条路径唯一的汇总口 |
| `scanFactorCandidates(rows, fields, opts)`（async） | `rows`,`fields`,`opts` | `Promise<{candidates,skipped}>` | 主线程串行版＝`computeFieldRaw`循环+`assembleCampScan`，无 Worker 时的兜底，每20字段让出一帧 |

#### 因子构建与配权

| 函数 | 输入 | 输出 | 角色 |
|---|---|---|---|
| `buildFactors(rows, candidates, fieldSpecs, winThreshold, opts)` | `rows`,`candidates:Candidate[]`（带camp），`fieldSpecs`，`winThreshold`，`opts:{shape:'trap'|'interval'}` | `{factors:Factor[], skipped}` | 扫描候选→可编辑因子集（内部调 `autoWeights`） |
| `autoWeights(factors)` | `factors:Factor[]`（带`interval.score`） | `Factor[]`（写回 `weight`，四舍五入到0.1、最大余数法保证总和=100） | 权重 ∝ `interval.score`（Wilson下界×√coverage，区间感知，**不是** `\|AUC-0.5\|`） |
| `factorCorrelations(rows, fields, opts)` | `rows`,`fields:string[]`,`opts:{threshold=0.7,minN=20}` | `[{a,b,rho,n}]`（按`\|rho\|`降序） | Spearman 秩相关找冗余因子对 |

#### 目标函数 / 边际贡献（"挑因子"核心判据）

| 函数 | 输入 | 输出 | 角色 |
|---|---|---|---|
| `scorePoolRho(rows, factorSet, missingPolicy)` | `rows`,`factorSet:Factor[]`,`missingPolicy` | `number`（Spearman(score,returnMax)）或 `NaN` | **当前默认目标函数**：全程点对点ρ，不分档不绑cutoff |
| `computeRankBuckets(pairs, winThreshold)` | `pairs:[{score,ret}]`,`winThreshold` | `{buckets:[{loScore,hiScore,medianRet,n,hitRate,hitCount}], maxBucketFrac}` 或 `null` | 分位数分桶，供 `bucketRankRho` 和 UI 散点图共用 |
| `bucketZigzag(buckets)` | `buckets`（同上） | `{inversionCount, worstDrop, inversions:[...]}` | 诊断"档命中率倒挂"（锯齿），推荐路径导出诊断用 |
| `bucketRankRho` / `scorePoolTierGain` / `scorePoolBucketRho` | — | — | 分层秩相关/分层增益口径，**代码保留，当前 UI 未启用调用** |
| `computeHeldOutDeltaRho(rows, currentFactors, candidate, camp, winThreshold, opts)` | `rows`,`currentFactors:Factor[]`,`candidate:Candidate`,`camp`,`winThreshold`,`opts:{shape,missingPolicy,buildRows,trainRatio=0.7,timeField='swapBeginTime',splitMethod='time'}` | `{baselineTrain,withTrain,deltaTrain,baselineTest,withTest,deltaTest,nTrain,nTest}` 或 `{error}` | **唯一的边际贡献口径**（2026-07-29 起）：区间/梯形只在train推导，目标函数train/test各评一次。「计算候选边际ρ贡献」按钮和「算推荐」候选预筛共用同一个函数/同一个数（deltaTest）——此前并存的样本内版 `factorMarginalRho`（无切分、挑因子无过拟合防护）已删除 |
| `permutationNullMarginalRho(rows, currentFactors, candidates, winThreshold, opts)` | `rows`,`currentFactors`,`candidates`,`winThreshold`,`opts:{shape,missingPolicy,buildRows=rows,trainRatio,timeField,splitMethod,permutations=20,seed,onProgress}` | `summarizeNullDistribution` 输入用的 `deltas:number[]`（连同 `attempted` 计数），或 `{error}` | 「跑置换零分布」核心：打乱 `returnMax` 后在【全量】打乱行上重新挖区间，再用 `computeHeldOutDeltaRho` 对每个候选评一次Δρ，重复 `permutations` 次——回答"纯噪声能凑出多大边际ρ"，用来校准候选表 0.005 阈值 |
| `summarizeNullDistribution(deltas, meta)` | `deltas:number[]`,`meta`（透传字段，如`permutations,candidates,attempted`） | `{n,q50,q90,q95,q99,max,deltas,...meta}` 或（样本<10时）`{error,deltas,...meta}` | 汇总零分布分位数；样本不够10个仍把 deltas 原样带回，供分片并行时主线程拼接后再汇总一次 |
| `permutationPValue(nullDist, delta)` | `nullDist`（`summarizeNullDistribution`结果）,`delta:number` | `number`（经验p值，`+1/+1`修正保证>0） | 单个候选的观测边际ρ在零分布里的经验p值 |

#### ρ 驱动配权

| 函数 | 输入 | 输出 | 角色 |

## 4. 关键数据结构

```js
// Candidate：assembleCampScan 输出的每一项（扫描候选）
{
  field: string,
  n: number, pos: number,               // 有效样本数、正类(高倍/输家)数
  auc: number, ci: {lo,hi}, direction: 'high'|'low',
  significant: bool, significantAdj: bool, pAdj: number,   // AUC的BH校正
  interval: {                            // 或 null
    lo, hi, n, pos, winRate, lift, coverage, wilsonLo, score,
    base, posTotal, total, pPermutation, pAdj, significantAdj,
  } | null,
  intervalError: string | null,
  missRate: number,
  mcapRho: number,   // 与进场市值的秩相关（fieldAudit.js），|ρ|大=可能只是"买小盘"的影子，非新规律
  camp: 'hero' | 'evil',
}

// Factor：因子池里的一条（buildFactors / autoWeights 输出）
{
  field: string, camp: 'hero' | 'evil',
  auc: number, direction: 'high'|'low',
  interval: {...} | null,   // 挖出的原始区间（诊断/展示用）
  missRate: number,
  weight: number,           // 0~100，autoWeights 归一，用户可编辑
  lo0, lo1, hi1, hi0: number,   // 梯形/矩形四点边界（可为±Infinity）
}

// Scored row：scoreRow/scoreRows 输出
{ row: Row, score: number, perFactor: number[], lowCoverage?: bool }

// Recommend path entry：recommendFactorPath 的 path[i]
{
  field, camp, testRho, inRho, deltaTest, deltaIn, overfit: bool,
  testBuckets, inBuckets,     // computeRankBuckets 结果
  testZigzag, inZigzag,       // bucketZigzag 结果
}

// Recommend 顶层返回：recommendFactorPool
{
  path,                        // 同上「Recommend path entry」结构数组，原样来自 recommendFactorPath
  factors: Factor[],           // 全样本精配权重后的完整因子集（采用即用）
  rhoBefore, rhoAfter, rhoTrain, rhoTest, overfit,  // 影子权重诊断
  nTrain, nTest, zeroedFields, n,
  heldoutCurve: { curve:[{k,testRho,testStd,nFolds,inRho}], recommendedCount, kBest, kMax, K, bestTestRho },
  recommendedCount, factorsTrimmed,
}
```

`ρ`（Spearman系数）主要出现在 `computeHeldOutDeltaRho`/`optimizeWeightsForRho`/
`recommendFactorPath`/`recommendFactorPool` 的返回值里（`deltaTest`/`rhoTrainBefore`等字段名）；
`AUC` 出现在 `Candidate.auc`/`Factor.auc`；权重字段统一叫 `weight`；排除标记不挂在候选/因子对象本身上，
而是单独存在 `factorExclusions.js` 的持久化列表里，通过 `camp+field` 复合键关联。

## 5. `FactorRecommendCard.jsx`（2026-07-29 由两张卡合并成一张）

以前这里是两张并列的卡片，本节原本是一张"该信哪个"的对照表。现在只剩一张，对照表删掉了——
但**为什么合并**值得留着，否则很容易再被拆回去：

| | 旧「因子推荐1」 | 旧「因子推荐2」 | 合并后 |
|---|---|---|---|
| 选字段 | held-out 贪心（每步切 train/test） | **全样本内贪心**，靠事后校验兜底 | ✅ 取 1 |
| 配权 | 只有 `autoWeights`，要手动再点 🎯 | 选完坐标上升精配权，采用即用 | ✅ 取 2 |
| 过拟合校验 | 每步 `overfit` 标记 + `testZigzag` | 事后影子权重（只用 train 拟合） | ✅ 两个都要 |
| 因子数 | 无 | K 折曲线 + 1-SE 给 k* | ✅ 取 2 |
| 采用 | onAdopt(合并) / onReplace(整体替换) | onAdopt(可截断到 k* 后整体替换) | onAdopt(specs) + onAdoptFactors(带权重) |

**合并的理由不是省代码**，是两张卡对同一个问题给两个答案、用户得判断信哪个；而且分歧恰好落在
方法论最要害处：旧推荐2 在同一批样本上挖边界又评估增量，正是 `computeHeldOutDeltaRho` 那次
统一（见 [readme.md](readme.md) 第 9 节）要修的毛病——事后校验只能说"整体过不过拟合"，
改变不了选的时候就已经被噪声带偏。

**删掉的东西**：`recommendFactorPoolFull`（它的全样本贪心循环）、`buildPathFromPool`/`buildPathFromZero`
（无人调用的薄包装）、`onReplace`/`replaceWithRecommended`（"整体替换"现在统一由带精配权重的
`onAdoptFactors` 承担，旧路径替换进去的是 `autoWeights` 权重，严格更差）、以及推荐卡里那道
`evaluateCandidatesWithWorkers` 候选预评估（贪心内部本来就会跳过评估不出来的候选，
而候选表的「计算候选边际ρ贡献」算的就是同一个数——纯重复一遍全量计算）。

**一个实测结论，别再想当然**：`minGain` 不是过拟合防线。概念漂移那条用例里（信号只在训练区间
成立），held-out 贪心**照样会选中**那个字段——从空池出发时首个因子的 `deltaTest` 就等于它自己的
验证段 ρ，实测 +0.009，数值约等于 0 但大于任何合理的地板值（0.001/0.003 都拦不住）。
真正认得出它的是：① 每步 `overfit` 标记（样本内 Δρ≈0.25 vs 验证段 ≈0.009）；② 路径标签上
显示的数字本身就是 0.009 而不是 0.25；③ 影子权重校验 rhoTrain≈0.38 vs rhoTest≈0.002。
相比旧的全样本内贪心（标签显示 0.25，得等事后校验才知道有问题），改进在①②，**不在"拒绝"**。

## 6. `FactorSopCard.jsx`

纯静态展示组件，默认折叠，把找因子的操作顺序固化成页面文案：
**扫 → 算 held-out 边际ρ（可先跑置换零分布校准阈值）→ 看「与市值ρ」排除市值影子字段 → 按边际ρ(test)挑
（不是AUC）→ 去冗余 → 按ρ最优配权 → 看test是否也涨 → 生成上线**，并列出"三个别踩的坑"。
